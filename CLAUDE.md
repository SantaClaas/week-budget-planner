# Week Budget Planner

A drag-and-drop week planner. Activities get a weekly or daily hour budget, the user puts blocks of them on a Monday–Sunday week, then moves and resizes the blocks, and each activity shows live how many hours are still left to place.

## Where things are

- [`docs/SPEC.md`](docs/SPEC.md): the behavior and design spec, split by topic in [`docs/spec/`](docs/spec/) and listed there. Read the overview and the **glossary** (which loads in every session), then the files for the feature you're building, before you start. Persistence, security, design and accessibility (what screen readers hear, the keyboard paths) load by themselves when you touch matching files.
- [`docs/guidelines/`](docs/guidelines/): how code is named, split, styled and checked, one file per kind of code, listed in [`docs/CODING-GUIDELINES.md`](docs/CODING-GUIDELINES.md). `principles.md` always applies; the others (HTML, TypeScript, CSS, Solid, database, tests) load by themselves when you touch matching files, through [`.claude/rules/`](.claude/rules/). Read the one for the code you're about to write before planning it.
- [`docs/LOADING.md`](docs/LOADING.md): what the page loads, in which order and why. When you add anything the page loads (a script, chunk, font, image, polyfill), give it a tier there and check the build output.
- **Design canvas: https://claude.ai/artifact/7WBfh6DXVehhUMeD6TnoCk** (private, ask the user for access). It is the visual reference for every screen and state, in Material 3 Expressive. Its tokens are extracted to [`docs/design/m3-tokens.css`](docs/design/m3-tokens.css).
- [`prototype/week-budget-planner.html`](prototype/week-budget-planner.html): a working single-file prototype in vanilla JS. It's the reference for behavior, except where [`docs/spec/changes-from-the-prototype.md`](docs/spec/changes-from-the-prototype.md) says otherwise. It is no longer the reference for the look, and its copy still says "tile" and "arm". It was built as a claude.ai artifact, so its `window.claude.use("db")` / `use("user")` code is platform-specific and won't run here. Its storage is replaced by in-browser SQLite (see [`docs/spec/persistence.md`](docs/spec/persistence.md)).
- **Reference project: [SantaClaas/flashcut](https://github.com/SantaClaas/flashcut)** (same author, Solid 2.0, public). The storage layer comes from it: Web Locks leader election plus a typed RPC proxy over BroadcastChannel (see [`docs/guidelines/database.md`](docs/guidelines/database.md)).
- [`icons/icons.json`](icons/icons.json), [`scripts/build-iconset.ts`](scripts/build-iconset.ts) and [`src/icons/iconset.svg`](src/icons/iconset.svg): the Material Symbols iconset. To add an icon, add it to the manifest and run `pnpm icons:fetch`. Use the official SVGs only, never the icon font. See [`docs/spec/design.md`](docs/spec/design.md).
- [`docs/design/m3-shapes.css`](docs/design/m3-shapes.css) and [`scripts/build-shapes.ts`](scripts/build-shapes.ts) (`pnpm shapes`): Google's Material 3 Expressive shapes as CSS `shape()` values, generated from Google's own Kotlin sources. Use them for activity shapes; never redraw them.
- [`examples/example-week.json`](examples/example-week.json): example plan data in the stored format.
- `docs/*.png`: screenshots of the prototype (old look).

## Stack

- **SolidJS 2.0**, which is still a release candidate as of October 2026. Pin exact versions and don't use ranges, since breaking changes between RCs are possible:
  - `solid-js@2.0.0-rc.14`
  - `@solidjs/web@2.0.0-rc.14` (DOM rendering and `render` live here in 2.0, not in `solid-js/web`)
  - `@solidjs/vite-plugin@3.0.0-next.47` (the 2.0 replacement for `vite-plugin-solid`)
  - `vite@8`, TypeScript, strict mode
  - Storage: `@tursodatabase/database-wasm` (SQLite in OPFS) with `drizzle-orm@1.0.0-rc.4` and `drizzle-kit@1.0.0-rc.4`, pinned. See [`docs/guidelines/database.md`](docs/guidelines/database.md) and [`docs/spec/persistence.md`](docs/spec/persistence.md), including the required **database export/import**.
  - Use pnpm, like flashcut (`pnpm dlx` or `pnpx` instead of `npx`).
  - Formatting and linting: `oxfmt` (`pnpm format`, `pnpm format:check`) and `oxlint` with type-aware rules through `oxlint-tsgolint` (`pnpm lint`), all pinned. CI runs both. Run them, and `pnpm typecheck`, before committing.
  - **Strict, with explained exceptions.** The lint and TypeScript are both strict, type assertions (`as`, `<T>`, `!`) are lint errors, and an exception needs a reason on its line (see [`docs/guidelines/typescript.md`](docs/guidelines/typescript.md)). Never `@ts-ignore`.
  - Node 22.18 or newer: the build scripts in [`scripts/`](scripts/) are TypeScript, run by Node directly.
  - Tests: Vitest for units (`pnpm test`), Playwright in [`e2e/`](e2e/) for the paths where a failure would cost the user their plan (`pnpm test:browser`; in a cloud container add `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/opt/pw-browsers/chromium`). See [`docs/guidelines/tests.md`](docs/guidelines/tests.md).
  - Hosting: GitHub Pages, with a service worker that adds the cross-origin isolation headers, and progressive enhancement down to private windows. See Hosting and Progressive enhancement in [`docs/spec/persistence.md`](docs/spec/persistence.md).
- **Material 3 Expressive, built with plain CSS.** Use the tokens in [`docs/design/m3-tokens.css`](docs/design/m3-tokens.css) and [`docs/spec/design.md`](docs/spec/design.md), and build the components yourself, without a component library. How the CSS is written (cascade layers, rem instead of px, intrinsic sizing, logical properties, forced colors) is in [`docs/guidelines/css.md`](docs/guidelines/css.md), and it holds for styles set from TypeScript too.
- **No HTML from strings.** A Content Security Policy with Trusted Types only lets the build's own templates be written as HTML (see [`docs/spec/security.md`](docs/spec/security.md)). Show user text as text, never through `innerHTML`.
- **Browser support:** a cutting-edge app for up-to-date browsers. Baseline Newly available features are fine. Use a fallback where one exists and is cheap, and list every feature without one in [`docs/spec/browser-support.md`](docs/spec/browser-support.md).
- **Expressive on purpose.** The app should feel playful and personal, with some whimsy: activity shapes, lively color, springy motion. Lean expressive wherever Google's guidance allows, but never at the cost of clutter, legibility or accessibility. See "Expressiveness" in [`docs/spec/design.md`](docs/spec/design.md).
- **Google is the only source for Material Design.** That means m3.material.io, the official [Material 3 Design Kit](https://www.figma.com/community/file/1035203688168086460/material-3-design-kit) in Figma, and Google's own code (androidx `material3/tokens`, material-color-utilities, Material Symbols, Google Fonts). Never take Material values or patterns from memory, third-party libraries (MUI, Vuetify, Flutter packages and the like), blog posts or other unofficial write-ups. **Only the user can approve a deviation** from Google's guidance. Ask before deviating, and record each approved deviation in [`docs/spec/design.md`](docs/spec/design.md). The Figma kit needs a signed-in account, so ask the user if you need it. m3.material.io builds its pages with JavaScript, so a plain fetch only gets "This website requires JavaScript": render it in Chromium instead (Playwright with the preinstalled browser, through `HTTPS_PROXY` in a cloud container) and read the `main` element's text. A cloud environment needs the domain allowed in its network settings.

Solid 2.0 is not 1.x, and most training data and online examples are 1.x. **Don't write Solid code from memory.** [`docs/guidelines/solid.md`](docs/guidelines/solid.md) lists the official sources to read first, starting with `node_modules/solid-js/CHEATSHEET.md`, and loads by itself when you touch [`src/`](src/).

## Modern Web Guidance (required)

This project uses Google Chrome's [Modern Web Guidance](https://github.com/GoogleChrome/modern-web-guidance) skill, installed into the repository: `.agents/skills/modern-web-guidance/` (with a symlink for Claude Code in [`.claude/skills/`](.claude/skills/)) and pinned in [`skills-lock.json`](skills-lock.json). It was installed with `pnpx modern-web-guidance@latest install`; update it with `pnpx modern-web-guidance@latest update` and commit the result.

**Use the `modern-web-guidance` skill before implementing any UI, CSS or client-side feature**, such as the grid layout, the sticky header and gutter, pointer-event dragging, the snackbar, menu and placing toolbar (consider the Popover API), the bottom sheet and dialogs (`<dialog>`), the activity forms and validation (`:user-invalid`), focus handling, dark mode tokens, spring-like easing with `linear()`, and View Transitions for block changes. Prefer the native platform pattern it returns over a library or a hand-rolled version. The skill runs its searches through the `modern-web-guidance` CLI. Use pnpm: `pnpx modern-web-guidance@latest search "<what you want to do>"`, then `retrieve "<id>"`.

## Working agreements

- **The consumer's needs come first.** Start from what the user (or, for an API, the program using it) needs, derive the interface from that, and the types and structure from the interface. Those needs outrank every other guideline. See "The consumer's needs come first" in [`docs/guidelines/principles.md`](docs/guidelines/principles.md).
- Match the prototype's interactions exactly, including the keyboard and touch paths, except for [`docs/spec/changes-from-the-prototype.md`](docs/spec/changes-from-the-prototype.md) or other changes the user asks for.
- **Ask before the browser asks.** Never trigger a browser permission prompt (persistent storage, location, camera and so on) without the app first explaining why in its own UI, with a button that makes the request. See Browser permissions in [`docs/spec/security.md`](docs/spec/security.md).
- Use the glossary in [`docs/spec/glossary.md`](docs/spec/glossary.md) for every name, in UI copy and in code: "block" (never "tile"), "slot", "length", "placing" (never "armed"), "left to place", "over budget". Where a technical concept already has a name, code can use it even when the copy says something friendlier ("color scheme" in code, "Theme" in the UI; see Names in [`docs/guidelines/principles.md`](docs/guidelines/principles.md)). Keep the copy plain. If you need a new term, add it to the glossary first.
- Follow [`docs/guidelines/`](docs/guidelines/) (see [`docs/CODING-GUIDELINES.md`](docs/CODING-GUIDELINES.md)): no abbreviations, functions start with a verb, modules named for what they are (no `lib` or `utils`), as few exports as possible, dependencies one way, and wait for about three repeats before pulling something out.
- Keep the browser tests in [`e2e/`](e2e/) passing, and add one when a new path could lose the user's data. Before calling the port done, also test it in a browser by hand: drag from the Activities list, move, resize from both edges, placing by tap on touch, adding a block from an empty slot (menu on desktop, bottom sheet on a phone), the phone navigation bar, undo, a reload that keeps state, two tabs open at once, a database export followed by an import of that file, both color themes, including the theme setting, and a private window or a browser with service workers blocked (the limited storage level).
